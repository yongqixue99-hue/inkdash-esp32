# 源码设计与踩坑记录

## 1. 设计目标

InkDash 的设备端只做四件事：联网、校验数据、保存最后一次有效结果、刷新电子纸。账号登录、数据整理和图片生成都留在电脑端。

这样设计有三个直接好处：

- ESP32 不保存 Codex 登录凭据；
- 接口变化时，只改电脑端，不必每次重刷设备；
- 断网和电脑关机后，设备还能显示最后一次有效页面。

![InkDash 源码设计](images/inkdash-source-design-codex-cn.png)

公开教程采用电脑直连墨水屏的局域网路径。没有强制中转服务，也没有绑定某一家云主机或服务商。

## 2. 数据从哪里来

### 2.1 本地会话层

Codex 会把会话遥测保存到用户目录：

```text
~/.codex/sessions/**/*.jsonl
```

`host/codex_usage.py` 扫描最近的 JSONL。它先用文本筛选 `token_count`，再解析数字事件。聊天消息和提示词不进入 InkDash 数据对象。

这一层可以得到：

- 当前周额度已用百分比；
- 剩余百分比；
- 重置时间；
- 这台电脑近 7 日产生的 Token。

它的范围是“当前设备上的本地会话”，无法天然代表整个账号。

### 2.2 账号统计层

`host/codex_profile.py` 从本机 Codex 登录文件读取访问令牌和账号 ID，然后请求：

```text
GET https://chatgpt.com/backend-api/wham/profiles/me
```

请求头使用：

```text
Authorization: Bearer <本机访问令牌>
ChatGPT-Account-Id: <本机账号 ID>
```

这一步发生在电脑内。响应被整理为每日 Token、账号累计 Token 和峰值，凭据不会写入返回给 ESP32 的 JSON。

该地址属于 Codex 桌面端使用的非公开后端，不承诺长期稳定。请求失败时，数据服务回退到本地会话层，页面范围改为 `WIN`；它不会把本地数字和账号数字相加。

## 3. 数据读取问题是怎么解决的

早期版本只读取本地会话文件。额度百分比能显示，Token 图也能画，但数字代表当前电脑，换一台电脑或查看账号累计时会对不上。

后续处理分成两层：

1. 本地会话读取保留，负责离线和接口故障时的降级；
2. 账号统计请求成功后，替换 Token 的统计口径；
3. 数据中加入 `usage_scope`，屏幕和日志能知道当前是 `ACCOUNT` 还是 `WIN`；
4. 设备严格校验七日明细、今日、七日合计和累计值之间的关系；
5. 任何一层失败都保留上次有效快照，不填演示数据。

这个改动解决了“画面有数字，但数字口径说不清”的问题。

## 4. 电脑端结构

电脑端对设备只暴露几个很小的接口：

| 路径 | 内容 |
|---|---|
| `/health` | 服务存活状态 |
| `/dashboard` | Codex 数字 JSON |
| `/server-dashboard` | 可选的通用服务器数字 JSON |
| `/wallpaper.bin` | 96,028 字节三色壁纸包 |
| `/health.bin` | 96,028 字节三色健康页 |

内部模块分工：

- `codex_usage.py` 管本地 JSONL；
- `codex_profile.py` 管账号统计请求与凭据边界；
- `dashboard_server.py` 合并数据、检查可选配置、提供 HTTP；
- `build_network_wallpaper.py` 把普通图片量化成黑白红两张位平面；
- `render_health_dashboard.py` 把七日健康 JSON 排版成图片包。

数据读取细节都藏在电脑端模块里。HTTP 层只拿一个标准快照，ESP32 也只认固定字段。

## 5. ESP32 端结构

### 5.1 启动与调度

`src/main.cpp` 负责串起流程：

1. 打开 OTA 健康日志；
2. 恢复上次页码；
3. 初始化触摸、电池和屏幕；
4. 恢复数字与图片缓存；
5. 连接 Wi-Fi；
6. 获取当前页数据并全刷；
7. 新 OTA 镜像通过全部健康检查后，才确认启动成功。

页面、网络、显示、存储和 OTA 各自放在独立模块。主流程只调用它们公开的少量操作。

### 5.2 数据接口与校验

`DashboardClient` 管 Wi-Fi、HTTP 和 JSON 校验。它拒绝：

- 百分比不在 0–100；
- 已用与剩余相加不等于 100；
- 日期格式错误；
- 七日数组长度不是 7；
- 今日不等于最后一个日桶；
- 七日合计与明细之和不一致；
- Token 与图表缩放值对不上；
- 响应过大、超时或 HTTP 非 200。

验证通过的数据才进入显示和缓存。

### 5.3 页面渲染

固定中文标签在电脑端生成成精确三色底图，动态数字在 ESP32 端绘制。这样可以避开运行时中文字体占用和编码问题，又能让数字保持实时。

页面模板流程：

```text
可编辑 SVG → 800×480 PNG → 黑色/红色 1-bit 位平面 → RLE C++ 资源
```

壁纸和健康页走另一条路径：电脑端直接生成完整位平面包，设备校验长度、尺寸和 CRC 后显示。

### 5.4 A/B 缓存

数字快照、页码、Wi-Fi、OTA 健康日志、壁纸和健康页都采用 A/B 记录：

1. 读取 A、B 两份；
2. 校验魔数、版本、长度、序号和校验和；
3. 选序号更新的有效记录；
4. 写入时先写非活动槽；
5. 读回确认后再把它当成新记录。

写入中断或突然断电时，旧槽仍可恢复。

## 6. 按键问题是怎么解决的

最初计划让前置按键像普通按键一样切换页面。实机检查后发现，椭圆按键接的是 `EN` 与 GND。按下会让 ESP32 重启，软件运行期间没有一个可轮询的 GPIO 电平。

最终方案沿用现有按键：

- 直接触摸 GPIO9/GPIO3 时，立即换页；
- EN 按键造成重启时，通过复位原因识别；
- 页码存进 A/B Flash；
- 外部/上电式复位后前进一页；
- 软件重启、看门狗和崩溃保持原页。

这个方案不需要改线。代价是每次按前置键都会重启、重新联网并全刷，约需 18 秒。完全断电再上电也可能被识别成下一页。

## 7. 两个 USB-C 的误判

第一次烧录使用外部接口时，电脑没有识别设备。后来改用内部接口才成功。

硬件关系如下：

- 内部 USB-C 的 D+/D− 接到 ESP32-C3 原生 USB，可进入 ROM 下载、烧录和查看 CDC 串口；
- 外部 USB-C 主要接供电/充电路径，当前结构没有形成可用烧录数据链路。

因此烧录教程把“设备管理器是否出现 `VID_303A`”作为判断依据，而不根据接口外形猜用途。

## 8. Wi-Fi 持久化问题

普通 NVS 在这块参考硬件上出现过保存不稳定。固件后来把 Wi-Fi 放进数据分区中的两个固定扇区，并保留旧记录迁移逻辑。

配网策略：

- 没有记录：立即打开受密码保护的配网热点；
- 有记录但短暂断网：后台每 30 秒重试，保留当前画面；
- 连续一小时无法关联：打开恢复热点；
- 连上新网络：先写 A/B 记录，再结束热点。

路由器重启不会立刻把屏幕切成配网页。

## 9. 断网与过期数据

设备使用三个状态：

- `LIVE`：本次请求成功，数据仍在有效期；
- `STALE`：本次失败或快照已过期，但有历史有效数据；
- `OFFLINE`：从未拿到有效数据。

Codex 可每 30 分钟轮询。只有屏幕上可见的数字、日期、图表或状态改变时才执行约 18 秒全刷。四小时维护刷新用于日期和电池。

## 10. OTA 设计

设备固件只保存 P-256 公钥。发布端保存私钥，并对 Manifest 中的硬件 ID、频道、版本号、文件大小、SHA-256 和下载 URL 签名。

升级过程：

1. 校验 Manifest 签名；
2. 拒绝旧版本、错误硬件、错误频道和越界 URL；
3. 把固件写入非活动 OTA 槽；
4. 校验完整 SHA-256；
5. 写入应用健康日志；
6. 重启到新槽；
7. 存储、Wi-Fi 和一次完整屏幕刷新都成功后确认；
8. 健康确认前再次复位，下一次启动回到旧槽。

OTA 默认关闭。公开复刻者需要生成自己的密钥并自行配置发布地址。

## 11. 安全边界

ESP32 中可以出现：

- 局域网数据地址；
- Wi-Fi 凭据；
- OTA 公钥；
- 已整理的数字和图片缓存。

ESP32 中不应出现：

- Codex 访问令牌；
- ChatGPT 账号 ID；
- Cookie；
- SSH 私钥；
- OTA 私钥；
- 聊天内容或完整会话文件。

公开仓库也不提交 `include/secrets.h`、`artifacts/`、`backups/` 和 `config/server-dashboard.json`。

## 12. 后续扩展方式

添加新数字页时，建议按现有边界扩展：

1. 电脑端先把原始数据整理为小而稳定的 JSON；
2. 在设备端建立严格数据结构和校验；
3. 固定标签进入 SVG 底图；
4. 动态数字在 ESP32 绘制；
5. 为快照增加独立或兼容的 A/B 记录；
6. 设计断网、过期和空数据表现；
7. 写原生记录测试和接口测试；
8. 最后才接入主页面循环。

这样新增数据源不会把账号登录、业务解析和屏幕驱动搅在一起。
